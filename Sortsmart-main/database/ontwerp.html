SortSmart database-ontwerp

Welke informatie moet SortSmart opslaan, en hoe? Van conceptueel klassendiagram via het relationeel representatiemodel naar een implementatiemodel in MySQL. Team: Bram, Houssam, Mohmad, Diese en Daniyal.

Stap 0

Welke informatie moet erin?

Uit het concept volgt dat de database vier soorten informatie moet bijhouden: waar de stations staan, hoe ze zijn opgebouwd (vakken per afvalfractie), wat er gebeurt bij het weggooien (scans en foutmeldingen zoals vloeistof of meerdere items), en het beheer (vulgraad, meldingen en legingen door facilitair en schoonmaak).

Gebruikers blijven anoniem

Studenten moeten binnen 5 seconden hun afval kwijt. Er is geen login en er worden geen persoonsgegevens van gebruikers opgeslagen (AVG).

Vier vakken per station

Papier, PMD, Rest en Etensresten, zoals in het mechanisch ontwerp. Elke fractie komt per station maar één keer voor.

Vulgraad wordt gemeten

We gaan ervan uit dat elk vak een afstandssensor heeft die de vulgraad doorgeeft. Boven een drempel ontstaat een melding.

Data voor Facilitair

Scans en legingen laten zien hoeveel er goed gescheiden wordt. Daarmee kan Facilitair aantonen dat de afvalstromen schoon blijven.

Stap 1 · conceptueel

Klassendiagram

Het klassendiagram beschrijft de werkelijkheid zonder technische sleutels: alleen klassen, attributen met datatype, associaties en multipliciteiten. [0..1] achter een attribuut betekent dat het niet verplicht is. De gevulde ruit tussen SorteerStation en Vak is een compositie: een vak bestaat niet zonder zijn station.

  • Een campus heeft 0..* stations; een station staat op precies 1 campus.
  • Een station bestaat uit 1..4 vakken; een vak hoort bij precies 1 station.
  • Een vak is voor precies 1 afvalfractie; een fractie komt voor in 0..* vakken.
  • Een itemtype hoort bij precies 1 fractie; een fractie heeft 0..* itemtypes.
  • Een station registreert 0..* scans; een scan hoort bij 1 station.
  • Een scan herkent 0..1 itemtype (niets bij meerdere items of niet herkend).
  • Een station genereert 0..* meldingen; een melding betreft 0..1 vak.
  • Een melding wordt door 0..1 medewerker afgehandeld.
  • Een vak wordt 0..* keer geleegd; elke leging wordt door 1 medewerker uitgevoerd.

Stap 2 · logisch

Relationeel representatiemodel

Elke klasse wordt een tabel. We voegen primaire sleutels toe en zetten de associaties om naar vreemde sleutels. Daarbij gelden deze regels:

1-op-veel

De vreemde sleutel komt aan de veel-kant. Voorbeeld: campus_id in SORTEERSTATION.

Compositie

VAK is een zwakke entiteit. De sleutel van het station wordt deel van de primaire sleutel: (station_id, vaknummer).

Optioneel (0..1)

De vreemde sleutel mag leeg zijn, zoals itemtype_id in SCAN en afgehandeld_door in MELDING.

Enumeraties

Een vaste lijst waarden wordt geen tabel maar een kolom met een CHECK-constraint. Afvalfractie heeft eigen attributen en wordt daarom wel een tabel.

onderstreept = primaire sleutelcursief = vreemde sleutel

CAMPUS (campus_id, naam, adres, postcode, plaats)

SORTEERSTATION (station_id, campus_id, serienummer, locatie_omschrijving, verdieping, installatiedatum, firmware_versie, status)

FK campus_id → CAMPUS

AFVALFRACTIE (fractie_id, naam, kleurcode, omschrijving)

VAK (station_id, vaknummer, fractie_id, capaciteit_liter, vulgraad_procent)

FK station_id → SORTEERSTATION · FK fractie_id → AFVALFRACTIE

ITEMTYPE (itemtype_id, fractie_id, naam, materiaal)

FK fractie_id → AFVALFRACTIE

SCAN (scan_id, station_id, itemtype_id, tijdstip, betrouwbaarheid, resultaat)

FK station_id → SORTEERSTATION · FK itemtype_id → ITEMTYPE

MEDEWERKER (medewerker_id, voornaam, tussenvoegsel, achternaam, email, rol)

LEGING (leging_id, station_id, vaknummer, medewerker_id, tijdstip, vulgraad_voor_leging, gewicht_kg)

FK (station_id, vaknummer) → VAK · FK medewerker_id → MEDEWERKER

MELDING (melding_id, station_id, vaknummer, afgehandeld_door, type, omschrijving, tijdstip_gemeld, status, afgehandeld_op)

FK station_id → SORTEERSTATION · FK (station_id, vaknummer) → VAK · FK afgehandeld_door → MEDEWERKER

Bouwen

SQL-script

Het volledige script maakt de database aan en vult hem met voorbeelddata. Het is getest op MariaDB: alle tabellen laden, en foute invoer (vaknummer 5, een gesorteerde scan zonder itemtype, een onbekende rol) wordt geweigerd.

-- =============================================================
-- SortSmart – relationeel implementatiemodel (MySQL 8.0+)
-- Team: Bram, Houssam, Mohmad, Diese, Daniyal
-- =============================================================

DROP DATABASE IF EXISTS sortsmart;
CREATE DATABASE sortsmart CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE sortsmart;

-- Campus waar SortSmart-stations staan
CREATE TABLE campus (
    campus_id   INT          NOT NULL AUTO_INCREMENT,
    naam        VARCHAR(100) NOT NULL,
    adres       VARCHAR(150) NOT NULL,
    postcode    CHAR(6)      NOT NULL,
    plaats      VARCHAR(80)  NOT NULL,
    CONSTRAINT pk_campus PRIMARY KEY (campus_id),
    CONSTRAINT uq_campus_naam UNIQUE (naam),
    CONSTRAINT ck_campus_postcode CHECK (postcode REGEXP '^[1-9][0-9]{3}[A-Z]{2}$')
);

-- Eén SortSmart-module bovenop een afvalbak
CREATE TABLE sorteerstation (
    station_id           INT          NOT NULL AUTO_INCREMENT,
    campus_id            INT          NOT NULL,
    serienummer          VARCHAR(30)  NOT NULL,
    locatie_omschrijving VARCHAR(150) NOT NULL,
    verdieping           TINYINT      NULL,
    installatiedatum     DATE         NOT NULL,
    firmware_versie      VARCHAR(20)  NOT NULL,
    status               VARCHAR(10)  NOT NULL DEFAULT 'Actief',
    CONSTRAINT pk_sorteerstation PRIMARY KEY (station_id),
    CONSTRAINT uq_station_serienummer UNIQUE (serienummer),
    CONSTRAINT fk_station_campus FOREIGN KEY (campus_id)
        REFERENCES campus (campus_id) ON UPDATE CASCADE ON DELETE RESTRICT,
    CONSTRAINT ck_station_status CHECK (status IN ('Actief','Onderhoud','Storing','Inactief'))
);

-- Afvalstroom: Papier, PMD, Rest, Etensresten
CREATE TABLE afvalfractie (
    fractie_id   INT          NOT NULL AUTO_INCREMENT,
    naam         VARCHAR(30)  NOT NULL,
    kleurcode    CHAR(7)      NOT NULL,
    omschrijving VARCHAR(255) NULL,
    CONSTRAINT pk_afvalfractie PRIMARY KEY (fractie_id),
    CONSTRAINT uq_fractie_naam UNIQUE (naam),
    CONSTRAINT ck_fractie_kleur CHECK (kleurcode REGEXP '^#[0-9A-Fa-f]{6}$')
);

-- Vak (zak/container) binnen een station – zwakke entiteit
CREATE TABLE vak (
    station_id        INT      NOT NULL,
    vaknummer         TINYINT  NOT NULL,
    fractie_id        INT      NOT NULL,
    capaciteit_liter  SMALLINT NOT NULL,
    vulgraad_procent  TINYINT  NOT NULL DEFAULT 0,
    CONSTRAINT pk_vak PRIMARY KEY (station_id, vaknummer),
    CONSTRAINT uq_vak_station_fractie UNIQUE (station_id, fractie_id),
    CONSTRAINT fk_vak_station FOREIGN KEY (station_id)
        REFERENCES sorteerstation (station_id) ON UPDATE CASCADE ON DELETE CASCADE,
    CONSTRAINT fk_vak_fractie FOREIGN KEY (fractie_id)
        REFERENCES afvalfractie (fractie_id) ON UPDATE CASCADE ON DELETE RESTRICT,
    CONSTRAINT ck_vak_nummer    CHECK (vaknummer BETWEEN 1 AND 4),
    CONSTRAINT ck_vak_capaciteit CHECK (capaciteit_liter > 0),
    CONSTRAINT ck_vak_vulgraad  CHECK (vulgraad_procent BETWEEN 0 AND 100)
);

-- Soort item dat de sensor kan herkennen (blikje, koffiebeker, ...)
CREATE TABLE itemtype (
    itemtype_id INT         NOT NULL AUTO_INCREMENT,
    fractie_id  INT         NOT NULL,
    naam        VARCHAR(60) NOT NULL,
    materiaal   VARCHAR(40) NOT NULL,
    CONSTRAINT pk_itemtype PRIMARY KEY (itemtype_id),
    CONSTRAINT uq_itemtype_naam UNIQUE (naam),
    CONSTRAINT fk_itemtype_fractie FOREIGN KEY (fractie_id)
        REFERENCES afvalfractie (fractie_id) ON UPDATE CASCADE ON DELETE RESTRICT
);

-- Elke keer dat iemand iets boven het scanplatform houdt
CREATE TABLE scan (
    scan_id          BIGINT       NOT NULL AUTO_INCREMENT,
    station_id       INT          NOT NULL,
    itemtype_id      INT          NULL,
    tijdstip         DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    betrouwbaarheid  DECIMAL(5,2) NULL,
    resultaat        VARCHAR(25)  NOT NULL,
    CONSTRAINT pk_scan PRIMARY KEY (scan_id),
    CONSTRAINT fk_scan_station FOREIGN KEY (station_id)
        REFERENCES sorteerstation (station_id) ON UPDATE CASCADE ON DELETE CASCADE,
    -- geen ON DELETE/UPDATE-actie: MySQL staat dat niet toe op een kolom in een CHECK
    CONSTRAINT fk_scan_itemtype FOREIGN KEY (itemtype_id)
        REFERENCES itemtype (itemtype_id),
    CONSTRAINT ck_scan_resultaat CHECK (resultaat IN
        ('Gesorteerd','MeerdereItems','VloeistofGedetecteerd','NietHerkend')),
    CONSTRAINT ck_scan_betrouwbaarheid CHECK (betrouwbaarheid BETWEEN 0 AND 100),
    -- een gesorteerd item moet herkend zijn
    CONSTRAINT ck_scan_gesorteerd CHECK (resultaat <> 'Gesorteerd' OR itemtype_id IS NOT NULL)
);

-- Facilitair-, schoonmaak- of beheermedewerker
CREATE TABLE medewerker (
    medewerker_id INT          NOT NULL AUTO_INCREMENT,
    voornaam      VARCHAR(50)  NOT NULL,
    tussenvoegsel VARCHAR(15)  NULL,
    achternaam    VARCHAR(80)  NOT NULL,
    email         VARCHAR(150) NOT NULL,
    rol           VARCHAR(12)  NOT NULL,
    CONSTRAINT pk_medewerker PRIMARY KEY (medewerker_id),
    CONSTRAINT uq_medewerker_email UNIQUE (email),
    CONSTRAINT ck_medewerker_rol CHECK (rol IN ('Facilitair','Schoonmaak','Beheerder'))
);

-- Het legen van een vak door een medewerker
CREATE TABLE leging (
    leging_id            INT          NOT NULL AUTO_INCREMENT,
    station_id           INT          NOT NULL,
    vaknummer            TINYINT      NOT NULL,
    medewerker_id        INT          NOT NULL,
    tijdstip             DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    vulgraad_voor_leging TINYINT      NOT NULL,
    gewicht_kg           DECIMAL(5,2) NULL,
    CONSTRAINT pk_leging PRIMARY KEY (leging_id),
    CONSTRAINT fk_leging_vak FOREIGN KEY (station_id, vaknummer)
        REFERENCES vak (station_id, vaknummer) ON UPDATE CASCADE ON DELETE CASCADE,
    CONSTRAINT fk_leging_medewerker FOREIGN KEY (medewerker_id)
        REFERENCES medewerker (medewerker_id) ON UPDATE CASCADE ON DELETE RESTRICT,
    CONSTRAINT ck_leging_vulgraad CHECK (vulgraad_voor_leging BETWEEN 0 AND 100),
    CONSTRAINT ck_leging_gewicht  CHECK (gewicht_kg >= 0)
);

-- Melding van een station (vak vol, storing, offline)
CREATE TABLE melding (
    melding_id           INT          NOT NULL AUTO_INCREMENT,
    station_id           INT          NOT NULL,
    vaknummer            TINYINT      NULL,
    afgehandeld_door     INT          NULL,
    type                 VARCHAR(15)  NOT NULL,
    omschrijving         VARCHAR(255) NULL,
    tijdstip_gemeld      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    status               VARCHAR(15)  NOT NULL DEFAULT 'Open',
    afgehandeld_op DATETIME     NULL,
    CONSTRAINT pk_melding PRIMARY KEY (melding_id),
    CONSTRAINT fk_melding_station FOREIGN KEY (station_id)
        REFERENCES sorteerstation (station_id) ON UPDATE CASCADE ON DELETE CASCADE,
    CONSTRAINT fk_melding_vak FOREIGN KEY (station_id, vaknummer)
        REFERENCES vak (station_id, vaknummer) ON UPDATE CASCADE ON DELETE CASCADE,
    CONSTRAINT fk_melding_medewerker FOREIGN KEY (afgehandeld_door)
        REFERENCES medewerker (medewerker_id) ON UPDATE CASCADE ON DELETE SET NULL,
    CONSTRAINT ck_melding_type   CHECK (type IN ('VakVol','SensorStoring','ServoStoring','Offline')),
    CONSTRAINT ck_melding_status CHECK (status IN ('Open','InBehandeling','Afgehandeld')),
    -- een afgehandelde melding heeft een tijdstip van afhandeling
    CONSTRAINT ck_melding_afgehandeld CHECK (status <> 'Afgehandeld' OR afgehandeld_op IS NOT NULL)
    -- bedrijfsregel (in de applicatie): een melding 'VakVol' heeft altijd een vaknummer
);

Verantwoording

Ontwerpkeuzes

  • Geen dubbele gegevens (3NF). Welk vak er bij een scan openging slaan we niet op: dat volgt uit station + itemtype → fractie → vak. Zo kan het nooit tegenstrijdig worden.
  • Eén fractie per station. De UNIQUE-constraint op (station_id, fractie_id) in VAK zorgt dat die afleiding altijd precies één vak oplevert.
  • Samengestelde vreemde sleutel. MELDING en LEGING verwijzen met (station_id, vaknummer) naar VAK. Een melding over vak 3 van station 7 kan daardoor alleen bestaan als dat vak echt bestaat.
  • Historie blijft bewaard. Een itemtype kan niet verwijderd worden zolang er scans naar verwijzen. Een medewerker die vertrekt, wordt bij meldingen op NULL gezet.
  • Bedrijfsregels in de database. CHECK-constraints bewaken percentages (0–100), postcodes (1234AB), kleurcodes (#RRGGBB) en de vaste waardenlijsten.
  • Uitbreiding later. Willen we recycling belonend maken (punten of een ranglijst), dan kan er een tabel DEELNEMER bij met een optionele koppeling vanuit SCAN, zonder dat de rest verandert.
